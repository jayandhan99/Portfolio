J1939 Fleet Telemetry Pipeline

MF4 → DBC Decode → Parquet → S3 → Grafana

Data Engineering IoT

Download Full Documentation (PDF) ↓

Overview

This project implements a two-step data pipeline for J1939 heavy vehicle telemetry: raw CAN bus recordings (MF4 format) are decoded against a J1939 DBC file and stored as columnar Parquet files in Amazon S3, then queried and visualized in Grafana via Amazon Athena. The pipeline was built and validated end-to-end using CSS Electronics open-source tooling, real J1939 sample data, and AWS cloud infrastructure.

What Was Built

Step What it does
Step 1 Pull MF4 file from S3 input bucket → decode using J1939 DBC → write Parquet files to S3 output bucket, organized by device ID / signal group / date.
Step 2 AWS Glue crawls the Parquet output bucket → catalogs tables in Athena → Grafana queries Athena and renders live time-series dashboards.

Tech Stack

Data catalog AWS Glue Crawler Scans Parquet output and registers tables in Glue catalog

S3 Output Structure

Each MF4 file decoded by the pipeline produces Parquet files organized by device ID, signal group, and date:

canedge-mf4-input-parquet/ 958D2219/ ← device serial number CAN1_EEC1_S00/ ← J1939 signal group (engine speed) 2020/01/13/ ← recording date 00002501_00002081.parquet CAN1_CCVS1_S00/ ← J1939 signal group (vehicle speed) 2020/01/13/ 00002501_00002081.parquet

Grafana Dashboards

Two J1939 signal groups were decoded from the sample data and are queryable in Athena:

Table J1939 Message Key Signals
can1_eec1_s00 EEC1 enginespeed (RPM) — engine controller #1
can1_ccvs1_s00 CCVS1 wheelbasedvehiclespeed (km/h) — cruise control / vehicle speed

Dashboard Queries

-- Engine Speed (RPM) SELECT t, enginespeed FROM can1_eec1_s00 ORDER BY t ASC -- Vehicle Speed SELECT t, wheelbasedvehiclespeed FROM can1_ccvs1_s00 ORDER BY t ASC

Visualization type: time series. Timestamp column: t. Both panels show 13 Jan 2020 08:47–09:00 UTC — approximately 13 minutes of real truck telemetry from a single CANedge device.

Findings

  • RPM–Speed Correlation (0.536): A moderate positive correlation between engine speed and vehicle speed across the recording window. This indicates the truck spent most of the ~13-minute session in low-load or idle conditions rather than active driving — engine RPM fluctuated fairly independently of vehicle speed, which stayed near zero throughout.
  • Constant fault flag (RPM > 1200 & speed < 5): The flag was true for nearly the entire window rather than intermittently, revealing that this particular recording is largely idle/stationary time — not a mix of driving and idling. So a fixed-threshold rule that’s meant to catch anomalies just matched the dominant condition instead, which is itself a useful finding: it shows the limits of static thresholds on this kind of dataset and points toward relative (e.g., statistical/z-score) methods as the better fit.

How to Reproduce

1

Clone repo

git clone https://github.com/CSS-Electronics/canedge-mdftoparquet-automation.git
2

Install dependencies and configure AWS

pip install -r requirements.txt aws configure
3

Upload MF4 files and DBC to S3 input bucket, then run the decoder

python run_test.py --cloud Amazon --input-bucket canedge-mf4-input --object-path AABBCCDD/00000001/FILE.MF4
4

Run the Glue crawler to catalog Parquet output

aws glue start-crawler --name canedge-crawler --region us-east-1
5

Start Grafana and query via Athena

docker run -d --name grafana -p 3000:3000 \ -e AWS_ACCESS_KEY_ID=... \ -e AWS_SECRET_ACCESS_KEY=... \ -e AWS_DEFAULT_REGION=us-east-1 \ grafana/grafana-enterprise

Key Observations

  • 145,534 raw CAN messages per MF4 file decode to ~21,542 named J1939 signals — a ~7x reduction via DBC filtering.
  • The pipeline auto-organizes output by device ID, signal group, and date — no manual partitioning needed.
  • Athena enables serverless SQL on S3 Parquet with no database to manage — query cost scales with data scanned, not uptime.
  • Engine speed (EEC1) and vehicle speed (CCVS1) are the two most diagnostically useful J1939 signals for fleet PdM — correlated anomalies between these two signals are a primary fault indicator.
